# ADR-0001: Стек приложения и его обоснование под условия ДЭ

- **Статус:** принято
- **Дата:** 2026-10-16
- **Часть плана:** Часть 0. Каркас репозитория и окружение

## Контекст

Нужно зафиксировать стек для тренировочного проекта по КИМ 09.02.07-3-2027 (Том 1).
Ограничения, которые диктует экзамен:

1. **Время.** Задание 1 — 1 ч 30 мин на БД + ER-диаграмму + бэкенд + 5 страниц фронтенда.
   Весь ДЭ БУ — 3 ч 30 мин. Любая настройка, которую нельзя воспроизвести за минуты,
   съедает баллы.
2. **Нет интернета** на рабочих местах. Библиотеки и фреймворки заранее размещаются в
   публичной папке сервера; участник ставит их офлайн.
3. **Окружение площадки.** КИМ перечисляет сервер «с поддержкой MySQL, PHP, SSH, SFTP,
   FTP, Python», отдельно — «среда для выполнения JavaScript» и «набор фреймворков —
   на усмотрение образовательной организации». Node.js и PostgreSQL прямо не названы.
4. **Вес критериев.** Подсистема безопасности — 16 б., интерфейс пользователя — 15 б.
   Стек должен давать быстрый и надёжный путь к auth, валидации и ролям.

## Варианты

### Вариант A — NestJS + PostgreSQL + React/Effector/Mantine (желаемый)

- За: один язык (TypeScript) на всём стеке; общие типы и схемы валидации между фронтом
  и бэком; у NestJS из коробки DTO-валидация, guard-ы, DI — это прямо работает на
  критерий «подсистемы безопасности»; Mantine закрывает формы, ошибки валидации,
  адаптив и компоненты — то есть Задание 2; Effector даёт предсказуемую бизнес-логику
  вне компонентов (критерий качества кода в Задании 3); команда уже знает стек.
- Против: не совпадает с перечнем ПО из КИМ — Node и Postgres придётся проверять в
  подготовительный день; самый тяжёлый `node_modules` из вариантов → офлайн-установка
  обязательна; NestJS даёт больше церемонии на единицу функционала, чем Express.

### Вариант B — PHP + MySQL (ближе всего к перечню ПО из КИМ)

- За: гарантированно есть на площадке; минимум настройки; быстрый старт без сборки.
- Против: команда не владеет стеком на нужном уровне; фронтенд всё равно придётся
  писать отдельно; нет общих типов; обучающая ценность для нас нулевая.

### Вариант C — Fastify/Express + PostgreSQL + React

- За: легче и быстрее поднимается, чем NestJS; меньше зависимостей.
- Против: валидацию, guard-ы и структуру модулей пишем руками — на экзаменационном
  таймере это минус, а не плюс; слабее работает на критерий «подсистемы безопасности».

## Решение

Выбран **Вариант A**: NestJS + PostgreSQL на бэкенде, React + Effector + Mantine UI на
фронтенде, TypeScript везде. Это заявленная цель обучения, и он лучше всего отрабатывает
два самых дорогих критерия инвариантной части.

Зафиксированные версии на момент принятия: Node 20+ (разработка на 24), TypeScript 5.9,
NestJS 12, React 19, Vite 8, Effector 23, Mantine 9.

**TypeScript намеренно не обновляем до 7.x**: NestJS опирается на `experimentalDecorators`
и `emitDecoratorMetadata`, и совместимость нового компилятора с этим пока не проверена.
Экзамен — не место для выяснения. Пересмотрим отдельным ADR.

Выбор ORM и способа работы с БД выносится в **ADR-0003** (Часть 1), выбор схемы
аутентификации — в **ADR-0004** (Часть 2).

## Последствия

- Положительные: общие типы и правила валидации в `packages/shared`; один тулчейн;
  DTO + guard-ы NestJS напрямую ложатся на требования задания; Mantine снимает
  значительную часть Задания 2.
- Отрицательные / принятый долг: тяжёлые зависимости; расхождение с перечнем ПО из КИМ;
  NestJS требует дисциплины по структуре модулей, иначе на таймере получается каша.
- **Что это требует на экзамене:**
  - Заранее подготовленный архив с `node_modules` и/или кэшем npm (см. ADR-0002) —
    проверить установку **без интернета**.
  - В подготовительный день убедиться, что на площадке есть Node 20+ и доступный
    PostgreSQL; если Postgres нет — работаем по плану отхода из ADR-0003 (SQL без
    диалект-специфичных конструкций, чтобы перенос на MySQL был механическим).
  - Офлайн-документация по NestJS, React, Effector, Mantine на рабочем месте.
  - Инструмент для ER-диаграммы, работающий офлайн.
- **Открытый вопрос к образовательной организации:** что именно входит в «набор
  фреймворков» и какая СУБД будет на общем сервере. До ответа держим план отхода.

## Связанные критерии КИМ

- Разработка подсистем безопасности ИС в соответствии с ТЗ — 16 б.
- Разработка интерфейса пользователя веб-приложений в соответствии с ТЗ — 15 б.
- Произведение разработки модулей ИС в соответствии с ТЗ — 6 б.
- Разработка веб-приложения в соответствии с ТЗ — 10 б.
- Оформление кода в соответствии со стандартом кодирования (Задание 3).
