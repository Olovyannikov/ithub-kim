# ADR-0011: Второй бэкенд на Python/MySQL

- **Статус:** принято
- **Дата:** 2026-10-19
- **Часть плана:** Часть 2Б. План отхода

## Контекст

КИМ описывает рабочее место участника с «программным обеспечением, обеспечивающим работу
удалённого сервера (с поддержкой MySQL, PHP, SSH, SFTP, Python)» и отдельно упоминает
«интегрированную среду разработки на языке Python». Node.js и PostgreSQL в перечне **не
названы**.

Основной стек выбран на TypeScript (ADR-0001) осознанно, но риск остаётся: если на
площадке не окажется Node, вся работа встанет. Эта часть — страховка.

Ключевое наблюдение, которое делает страховку дешёвой: **фронтенд переписывать не
придётся.** Он обращается к относительному `/api`, поэтому второй бэкенд, реализующий тот
же контракт, подключается заменой прокси. Поэтому в Части 2 и был описан контракт
(`docs/api`).

## Главный риск и что с ним делать

Две реализации одного API неизбежно расходятся. Расходятся они в самом дорогом месте — в
**текстах и правилах из ТЗ**: подписи статусов, способы оплаты, сообщения об ошибках,
регулярные выражения полей. Эксперт сверяет их с текстом КИМ дословно, и расхождение
стоит баллов по двум критериям сразу.

Решение: **правила не дублируются, а переносятся**. Скрипт `pnpm shared:python` читает
собранный `@kim/shared` и генерирует `apps/backend-py/app/shared_generated.py`. Файл
помечен как сгенерированный и правится только через источник. Так единственным источником
истины остаётся `packages/shared`, как и требует ADR-0005.

## Решение 1: фреймворк — FastAPI

|                          | FastAPI                  | Flask                 | Django + DRF  |
| ------------------------ | ------------------------ | --------------------- | ------------- |
| Валидация тела запроса   | **Pydantic из коробки**  | руками или расширение | сериализаторы |
| Описание контракта       | **OpenAPI генерируется** | расширение            | расширение    |
| Объём на одну задачу     | небольшой                | небольшой             | большой       |
| Близость к нашему NestJS | **высокая**              | средняя               | низкая        |

Выбран **FastAPI**. Решающее: он ближе всего к тому, что уже написано на NestJS —
валидация описывается схемами, ошибки перехватываются единым обработчиком, контракт
выгружается сам. Порт получается переводом, а не переписыванием.

Django отвергнут не из-за качества: он тянет свою ORM, миграции, админку и слой
сериализаторов. Для страховочной реализации одного и того же API это объём, который под
таймером не окупается.

## Решение 2: работа с базой — SQLAlchemy, таблицы из моделей

ORM — **SQLAlchemy 2.x**, драйвер — **PyMySQL**: чистый Python, ничего не собирается при
установке, что важно для офлайн-площадки (та же логика, что в ADR-0004 про пароли).

Миграций намеренно нет: таблицы создаются из моделей при старте (`create_all`). Для
основного бэкенда такой подход отвергнут в ADR-0003 — там нужна воспроизводимая история
схемы. Здесь приоритет другой: это запасной путь, который разворачивается на чужой машине
за минуты, и схема у него ровно одна — та, что уже описана ER-диаграммой. Решение
осознанное, а не забытое.

## Решение 3: совместимость с основным бэкендом

Три вещи сделаны так, чтобы два бэкенда были взаимозаменяемы для одного и того же клиента:

1. **Пароли.** Формат `scrypt$N$r$p$соль$хеш` из ADR-0004 разбирается встроенным
   `hashlib.scrypt`. То есть учётные записи, созданные одним бэкендом, работают во втором
   без перехеширования.
2. **Сессия.** Тот же токен HS256 в той же httpOnly-cookie `conf_session` с тем же
   секретом `JWT_SECRET`. Пользователь, вошедший через один бэкенд, остаётся вошедшим при
   переключении на другой.
3. **Ошибки.** Тот же формат `{ statusCode, message, errors }` — фронтенд раскладывает их
   по полям формы тем же кодом.

Ни одно из трёх не потребовало правок во фронтенде. Это и есть проверка того, что контракт
из Части 2 описан достаточно.

## Что остаётся несовместимым

- **СУБД.** PostgreSQL против MySQL — базы разные, данные между ними не переносятся сами.
  Это и не требуется: запасной бэкенд поднимается со своей базой и своими сидами.
- **Индекс по датам** из ADR-0009 переносится, триграммного индекса в MySQL нет — он и в
  основном бэкенде был отвергнут по результатам замера.

## Последствия

- Положительные: при отсутствии Node на площадке работа не встаёт; контракт API проверен
  второй независимой реализацией — это сильнее любой документации; правила из ТЗ
  физически не могут разойтись, потому что переносятся скриптом.
- Отрицательные / принятый долг: вторая реализация требует поддержки при каждом изменении
  контракта; `create_all` вместо миграций; зависимости Python нужно отдельно положить в
  офлайн-хранилище (`pip download` в каталог колёс).
- **Что это требует на экзамене:** решение «какой бэкенд поднимаем» принимается в
  подготовительный день, по факту наличия Node и СУБД, а не в день экзамена.
