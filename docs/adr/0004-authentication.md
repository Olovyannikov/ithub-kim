# ADR-0004: Аутентификация, сессии и хеширование паролей

- **Статус:** принято
- **Дата:** 2026-10-16
- **Часть плана:** Часть 2. Backend: безопасность и API

## Контекст

Это самое дорогое решение в проекте. Критерий «Разработка подсистем безопасности
информационной системы в соответствии с техническим заданием» — **16 баллов из 75**, и он
же единственный критерий, который присутствует во всех видах аттестации, включая ПА.

Что требует ТЗ:

- регистрация с уникальным логином и паролем от 8 символов (Задание 1, п. 1);
- авторизация с сообщениями при некорректном вводе (п. 2);
- пользователь видит **свои** заявки (п. 3);
- панель администратора доступна по логину `Conf2027` и паролю `Demo77` (п. 5).

Ограничения: нет интернета (значит, никаких нативных модулей, которые собираются при
установке), жёсткий таймер, и приложение должно подниматься на чужой машине за минуты.

## Варианты: способ хранения сессии

### Вариант A — серверные сессии (`express-session` + хранилище)

- За: мгновенный отзыв сессии; привычная модель.
- Против: хранилище в памяти теряет сессии при каждом перезапуске — а на экзамене бэкенд
  перезапускается постоянно, и каждый раз придётся логиниться заново; хранилище в
  PostgreSQL — это ещё одна зависимость и ещё одна таблица.

### Вариант B — JWT в localStorage

- За: простая реализация, много примеров.
- Против: токен доступен из JavaScript, то есть любая XSS уносит сессию. Для критерия
  «подсистемы безопасности» это ровно та ошибка, которую ищут.

### Вариант C — JWT в httpOnly-cookie

- За: токен недоступен из JavaScript; сервер не хранит состояние, поэтому перезапуск не
  разлогинивает; `@nestjs/jwt` — одна зависимость; выход реализуется очисткой cookie.
- Против: отозвать выданный токен досрочно нельзя.

## Решение по сессии

**Вариант C: JWT в httpOnly-cookie.**

- Cookie: `httpOnly`, `sameSite: 'lax'`, `secure` только когда приложение за HTTPS,
  `path: '/'`, срок жизни 7 дней — столько же, сколько у токена.
- В токене лежит **только идентификатор пользователя** (`sub`). Роль и остальные данные
  guard каждый раз читает из базы. Это на один запрос дороже, зато смена роли действует
  сразу, а не после перелогина, и в токене нет данных, которым можно было бы устареть.
- Невозможность досрочного отзыва принята осознанно: в системе нет ни «выйти на всех
  устройствах», ни блокировки пользователя — требований такого рода в ТЗ нет.

**CSRF.** Отдельную библиотеку не берём, и вот почему: cookie выставлена с
`SameSite=Lax`, фронтенд и API работают с одного источника (локально — через прокси Vite,
на площадке — за общим сервером), а все изменяющие операции идут через `fetch` с
`Content-Type: application/json`, который браузер не отправит кросс-сайтово без CORS-разрешения.
CORS настроен на единственный источник. Решение зафиксировано здесь, чтобы на защите
отвечать по существу, а не «мы про это не подумали».

## Варианты: хеширование пароля

|                               | `bcrypt`   | `argon2`   | `bcryptjs` | `scrypt` из `node:crypto` |
| ----------------------------- | ---------- | ---------- | ---------- | ------------------------- |
| Нативная сборка при установке | **да**     | **да**     | нет        | нет                       |
| Зависимостей                  | 1 + сборка | 1 + сборка | 1          | **0**                     |
| Работает офлайн из коробки    | рискованно | рискованно | да         | **да**                    |

`bcrypt` и `argon2` — нативные модули. На офлайн-машине их установка зависит от наличия
готового бинарника под эту платформу, иначе начинается сборка из исходников. Проверять
это в день экзамена нельзя.

## Решение по хешированию

**`scrypt` из встроенного `node:crypto`.** Ноль зависимостей, ничего не собирается,
алгоритм входит в рекомендации OWASP для хранения паролей.

Параметры и формат хранения:

```
scrypt$16384$8$1$<salt-base64>$<hash-base64>
```

- `N = 16384`, `r = 8`, `p = 1`, длина ключа 64 байта — параметры лежат **внутри строки
  хеша**, поэтому их можно будет поднять позже, не ломая уже сохранённые пароли.
- Соль — 16 случайных байт на каждый пароль.
- Сравнение через `timingSafeEqual`, чтобы не утекало время сравнения.

Алгоритм спрятан за `PasswordService` с двумя методами, `hash` и `verify`. Если на защите
понадобится именно bcrypt (как более «ожидаемый» вариант), заменяется только внутренность
сервиса: `bcryptjs` — чистый JS и тоже ставится офлайн.

## Роли и доступ

- Роль — поле `users.role` (`user` | `admin`), ограничено `CHECK` на уровне базы
  (ADR-0003).
- `JwtAuthGuard` читает cookie, проверяет подпись, загружает пользователя и кладёт его в
  запрос. Применяется глобально; публичные эндпоинты помечаются декоратором `@Public()`.
  Глобальный guard с явными исключениями, а не наоборот: забыть повесить защиту проще, чем
  забыть открыть доступ, и цена ошибки несимметрична.
- `RolesGuard` + `@Roles('admin')` закрывают панель администратора.
- Пользователь видит только свои заявки: фильтр по `user_id` ставится **в сервисе**, а не
  приходит из запроса. Клиент не может попросить чужие данные, потому что ему просто
  нечего для этого передать.

## Администратор из ТЗ

Логин `Conf2027` и пароль `Demo77` заданы КИМ жёстко. Здесь важная деталь: **этот пароль
не проходит нашу собственную валидацию** — в ТЗ требуется минимум 8 символов, а в `Demo77`
их шесть. Поэтому администратор создаётся сид-скриптом напрямую, минуя DTO регистрации:
правила валидации распространяются на регистрацию пользователей, а не на сидирование.
Логин `Conf2027` при этом подходит под правило «латиница и цифры, не менее 6 символов».

## Защита от перебора

`@nestjs/throttler` на эндпоинтах входа и регистрации. Одна зависимость, официальный пакет
Nest. `helmet` — на заголовки безопасности.

Значения вынесены в переменные `AUTH_THROTTLE_LIMIT` и `AUTH_THROTTLE_TTL`, по умолчанию
10 попыток в минуту. Изначально стояло 5, и это оказалось опасно для самой защиты работы:
сквозные проверки, делающие около пяти входов за прогон, на втором прогоне подряд получали
429 — всё, что связано со входом, переставало работать. **На защите эффект был бы тот же:**
эксперт пару раз ошибается паролем, пробует ещё, и приложение на минуту перестаёт пускать
всех с этого адреса — выглядит как поломка. Десять попыток перебор по-прежнему
останавливают, а живого человека нет.

Сообщение при неудачном входе — одно и то же независимо от того, не найден логин или не
совпал пароль (`Неверный логин или пароль` из `VALIDATION_MESSAGES`). Иначе форма входа
превращается в способ узнать, какие логины существуют.

## Последствия

- Положительные: перезапуск бэкенда не разлогинивает — на экзамене это экономит время
  на каждом цикле правки; токен недоступен из JS; ноль нативных зависимостей; алгоритм
  хеширования заменяется в одном файле.
- Отрицательные / принятый долг: нельзя отозвать выданный токен; guard делает
  дополнительный запрос к базе на каждый защищённый запрос.
- **Что это требует на экзамене:** в `.env` должен быть `JWT_SECRET`; отрепетировать
  порядок «сущность → DTO → сервис → контроллер → guard»; помнить, что администратор
  создаётся сидом, а не через форму регистрации.

## Связанные критерии КИМ

- Разработка подсистем безопасности ИС в соответствии с ТЗ — **16 б.**
- Произведение разработки модулей ИС в соответствии с ТЗ — 6 б.
