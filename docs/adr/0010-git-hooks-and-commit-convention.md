# ADR-0010: Git-хуки (lefthook) и стандарт сообщений коммитов

- **Статус:** принято
- **Дата:** 2026-10-16
- **Часть плана:** Часть 0. Каркас репозитория и окружение

## Контекст

КИМ прямо требует: «Выполняйте коммиты хотя бы в начале и в завершении выполнения
задания». История коммитов — то, по чему эксперт видит ход работы. При этом критерий
Задания 3 требует оформления кода по стандарту кодирования, а на таймере в 1 ч 30 мин
легко закоммитить несформатированный или не компилирующийся код.

Нужен механизм, который держит стандарт автоматически, но **не может заблокировать
коммит в критический момент**.

За основу взят рабочий конфиг из [Olovyannikov/FSD-example](https://github.com/Olovyannikov/FSD-example/blob/04-features/lefthook.yml).

## Варианты

### Вариант A — lefthook

- За: один бинарник, конфиг в YAML, нативная поддержка групп и `piped`/`parallel`,
  работа со `{staged_files}`, быстрый запуск; уже используется в наших проектах.
- Против: ставится через postinstall-скрипт, который pnpm по умолчанию блокирует —
  нужен явный `allowBuilds` (см. ADR-0002).

### Вариант B — husky + lint-staged

- За: самый распространённый вариант, много примеров.
- Против: два пакета вместо одного, конфиг размазан по трём файлам, медленнее.

### Вариант C — без хуков, только CI

- За: ничего не мешает коммитить.
- Против: CI на экзаменационной площадке нет; стандарт кодирования не удержать.

## Решение

**lefthook** (вариант A). Структура конфига повторяет референс из FSD-example, но
подключены только те проверки, инструменты для которых уже установлены. Остальные группы
оставлены закомментированными с привязкой к части плана, чтобы включать их по мере
прохождения:

| Хук          | Что делает сейчас                                          | Что добавится позже                                                           |
| ------------ | ---------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `pre-commit` | ESLint по staged-файлам, Prettier с автофиксом и `git add` | границы FSD (Часть 3), stylelint (Часть 5), циклические зависимости (Часть 6) |
| `commit-msg` | commitlint, Conventional Commits                           | —                                                                             |
| `pre-push`   | `pnpm typecheck` по всем пакетам                           | модульные тесты (Часть 2)                                                     |

Тяжёлые проверки намеренно разнесены: в `pre-commit` только быстрое и по staged-файлам,
полный `typecheck` — в `pre-push`, который на экзамене не выполняется (push идёт в
индивидуальный репозиторий, но проверка типов не должна задерживать обязательный коммит).

**Commitizen из референса не берём**: `cz --hook` интерактивен, а под таймером
интерактивный диалог на каждом коммите — потеря времени. commitlint оставляем: он только
проверяет сообщение и не трогает код.

`subject-case` в commitlint отключён, потому что тело сообщения пишем по-русски;
`header-max-length` поднят до 120 символов.

## Последствия

- Положительные: несформатированный код физически не попадает в историю; сообщения
  коммитов единообразны и читаемы для эксперта; одна команда (`pnpm install`) ставит хуки
  благодаря `prepare: lefthook install`.
- Отрицательные / принятый долг: хук добавляет секунды к каждому коммиту; commitlint
  может отклонить сообщение.
- **Аварийный выход, который надо помнить на экзамене:**

  ```bash
  LEFTHOOK=0 git commit -m "..."
  git commit --no-verify -m "..."
  ```

  Это зафиксировано комментарием в самом `lefthook.yml` — чтобы под таймером не
  вспоминать синтаксис.

- **Что это требует на экзамене:** `lefthook` ставится из офлайн-хранилища pnpm, и
  `allowBuilds` должен быть в `pnpm-workspace.yaml`, иначе бинарник не скачается и хуки
  не синхронизируются. Проверяется в Части 7.

## Связанные критерии КИМ

- Оформление кода в соответствии со стандартом кодирования (Задание 3).
- Требование задания о коммитах в начале и в конце выполнения.
