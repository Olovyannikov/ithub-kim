# ADR-0005: Валидация — единые правила для фронтенда и бэкенда

- **Статус:** принято
- **Дата:** 2026-10-16
- **Часть плана:** Часть 2. Backend: безопасность и API

## Контекст

ТЗ задаёт правила полей дословно (Задание 1, п. 1):

| Поле    | Правило из ТЗ                                     |
| ------- | ------------------------------------------------- |
| Логин   | латиница и цифры, не менее 6 символов, уникальный |
| Пароль  | минимум 8 символов                                |
| ФИО     | символы кириллицы и пробелы                       |
| Телефон | формат `8(XXX)XXX-XX-XX`                          |
| Email   | формат электронной почты                          |

Все поля обязательны. Задание 2 добавляет: «Ошибки валидации должны отображаться **на
форме**» — то есть недостаточно вернуть 400, ответ должен указывать, **в каком поле**
ошибка.

Главный риск — расхождение клиентской и серверной валидации. Если фронтенд пропускает то,
что отбивает бэкенд (или наоборот), это прямо бьёт по критерию «подсистемы безопасности»
(16 баллов) и выглядит на проверке как недоделанная работа.

Библиотека выбрана заранее: **`class-validator`** (решение зафиксировано заказчиком работы).

## Варианты: где живёт правило

### Вариант A — правила описаны дважды, в DTO и в форме

- За: ничего не нужно проектировать.
- Против: два источника истины. Любая правка расходится молча.

### Вариант B — схемы на `zod` в `packages/shared`, бэкенд валидирует ими же

- За: один артефакт на обе стороны.
- Против: отказ от `class-validator`, то есть от штатного `ValidationPipe` и от связки с
  `@nestjs/swagger`; плюс лишняя зависимость.

### Вариант C — в `@kim/shared` лежат регулярные выражения и тексты сообщений, обе стороны строят валидацию из них

- За: правило и его формулировка существуют в единственном месте; каждая сторона
  использует родной для себя механизм — `class-validator` на бэкенде, `@mantine/form` на
  фронтенде; не нужны лишние зависимости.
- Против: сам «склеивающий» код написан дважды — но он тривиален и не содержит правил.

## Решение

**Вариант C.** `packages/shared/src/validation.ts` уже содержит `LOGIN_PATTERN`,
`PASSWORD_MIN_LENGTH`, `FULL_NAME_PATTERN`, `PHONE_PATTERN`, `EMAIL_PATTERN` и
`VALIDATION_MESSAGES`. Это единственный источник истины.

- **Бэкенд:** DTO с декораторами `class-validator`, где и шаблон, и текст сообщения
  берутся из `@kim/shared`:

  ```ts
  @Matches(LOGIN_PATTERN, { message: VALIDATION_MESSAGES.login })
  login: string;
  ```

- **Фронтенд:** валидаторы `@mantine/form` строятся из тех же констант (Часть 3–4).

Жёсткое правило: **в DTO и в компонентах не появляется ни одного регулярного выражения и
ни одной текстовой формулировки ошибки.** Всё только ссылкой на `@kim/shared`. Это
проверяемое глазами условие на ревью.

## Формат ответа с ошибками

Штатный `ValidationPipe` отдаёт плоский массив строк — по нему нельзя разложить ошибки по
полям, а Задание 2 требует показывать их на форме. Поэтому `exceptionFactory` формирует
ответ по полям:

```json
{
  "statusCode": 400,
  "message": "Проверьте правильность заполнения полей",
  "errors": {
    "login": "Логин: латиница и цифры, не менее 6 символов",
    "phone": "Телефон в формате 8(XXX)XXX-XX-XX"
  }
}
```

Одно поле — одно сообщение: на форме всё равно показывается одна строка под полем, а
массив сообщений только усложнил бы фронтенд.

Ошибки уровня бизнес-правил отдаются в том же формате, чтобы фронтенд обрабатывал их
одним кодом:

- занятый логин → `409` с `errors: { login: VALIDATION_MESSAGES.loginTaken }`;
- неверные учётные данные → `401` с `errors: { login: VALIDATION_MESSAGES.credentials }`
  (сообщение одинаковое для несуществующего логина и неверного пароля — см. ADR-0004).

## Настройки ValidationPipe

```ts
new ValidationPipe({
  whitelist: true, // отбросить всё, что не объявлено в DTO
  forbidNonWhitelisted: true, // и сообщить об этом, а не промолчать
  transform: true, // привести типы к объявленным в DTO
  stopAtFirstError: true, // по одному сообщению на поле
  exceptionFactory, // ошибки по полям, см. выше
});
```

`whitelist` вместе с `forbidNonWhitelisted` — это и есть защита от присвоения лишних
полей: даже если клиент отправит `role: "admin"` в теле регистрации, запрос будет
отклонён, а не «частично применён».

## Что валидируется только на сервере

Клиентскую проверку легко обойти, поэтому на сервере остаются правила, которых на
фронтенде нет вообще:

- уникальность логина (запрос к базе);
- существование помещения с указанным `roomId`;
- принадлежность заявки текущему пользователю;
- допустимость перехода статуса (только администратор, только в «Мероприятие назначено»
  или «Завершено»);
- право оставить отзыв (`canLeaveReview` — только по завершённому мероприятию);
- отсутствие второго отзыва на ту же заявку.

Клиентская валидация — это удобство для пользователя. Серверная — это и есть подсистема
безопасности.

## Последствия

- Положительные: правило и его формулировка живут в одном месте; ошибки сразу в виде,
  пригодном для показа на форме; `whitelist` закрывает присвоение лишних полей.
- Отрицательные / принятый долг: `class-validator` 0.15 и `class-transformer` 0.5 — две
  зависимости и рантайм-декораторы; ошибки маппинга видны только при выполнении.
- **Уточнение от 19.10.2026.** Вариант B отвергался в том числе из-за лишней зависимости
  `zod`. В Части 3 выяснилось, что `zod` всё равно приезжает на фронтенд как peer-зависимость
  `@effector/router` (ADR-0006), так что этот довод больше не действует. Решение всё равно
  оставляем: `class-validator` остаётся правильным выбором для DTO в NestJS, а наличие
  `zod` на фронтенде ничем не помогает серверным DTO. Переписывать валидацию ради
  единообразия — работа без выигрыша в баллах.
- **Что это требует на экзамене:** помнить, что правила не пишутся в DTO руками, а
  импортируются; отрепетировать, как выглядит ответ с `errors` и как фронтенд
  раскладывает его по полям формы.

## Связанные критерии КИМ

- Разработка подсистем безопасности ИС в соответствии с ТЗ — 16 б.
- Разработка интерфейса пользователя (ошибки валидации на форме) — 15 б.
- Формирование требований к дизайну на основе анализа предметной области — 4 б.
