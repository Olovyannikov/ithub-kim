# ADR-0002: Структура монорепозитория и менеджер пакетов

- **Статус:** принято
- **Дата:** 2026-10-16
- **Часть плана:** Часть 0. Каркас репозитория и окружение

## Контекст

Бэкенд и фронтенд пишутся на TypeScript и делят между собой домен: статусы заявки,
способы оплаты, роли, правила валидации полей из ТЗ (логин, пароль, ФИО, телефон, email).
Дублировать эти правила в двух местах — прямой путь к расхождению фронтовой и серверной
валидации, а это критерий «подсистемы безопасности» (16 б.).

Ограничения экзамена: нет интернета на рабочих местах; на развёртывание проекта должно
уходить минуты, а не десятки минут; на площадке может не быть ничего, кроме Node.

## Варианты

### Структура

#### Вариант A — монорепозиторий `apps/*` + `packages/*`

- За: общий код в одном месте, один `install`, одна конфигурация линтера и форматтера,
  один коммит на сквозное изменение (а коммиты по заданию обязательны).
- Против: нужна настройка workspaces; чуть сложнее, чем один каталог.

#### Вариант B — два отдельных репозитория

- За: предельно просто.
- Против: общий домен копируется руками; на экзамене нужно вести два репозитория и
  коммитить в оба — лишние действия под таймером.

#### Вариант C — монорепозиторий с Nx / Turborepo

- За: кэш сборок, графы задач, генераторы.
- Против: лишний слой для проекта из трёх пакетов; ещё одна тяжёлая зависимость для
  офлайн-установки; время на изучение не окупается в рамках 3 ч 30 мин.

### Менеджер пакетов

#### Вариант A — pnpm через corepack

- За: быстрая установка; контентно-адресуемое хранилище, которое легко подготовить
  офлайн; строгая изоляция зависимостей (пакет не видит то, что не объявил);
  первоклассная поддержка workspaces; `packageManager` + corepack фиксируют версию
  менеджера, и на любой машине воспроизводится один и тот же `install`.
- Против: по умолчанию `node_modules` построен на симлинках в глобальное хранилище —
  такой каталог **нельзя просто скопировать** на другую машину; на экзаменационной
  машине нужен либо подготовленный store, либо `node-linker=hoisted`.

#### Вариант B — npm workspaces

- За: ничего не нужно устанавливать дополнительно; `node_modules` — реальные файлы,
  каталог переносится копированием.
- Против: медленнее; слабее изоляция; скрипты в workspaces выполняются последовательно.

## Решение

**Структура — Вариант A**, монорепозиторий:

```
apps/backend   @kim/backend   NestJS + PostgreSQL
apps/frontend  @kim/frontend  React + Effector + Mantine
packages/shared @kim/shared  домен, константы, правила валидации
```

**Менеджер пакетов — pnpm, версия закреплена через corepack.** В корневом
`package.json` стоит `"packageManager": "pnpm@12.14.0"`; разработчик один раз выполняет
`corepack enable`. Nx/Turborepo не берём: для трёх пакетов хватает pnpm workspaces и
`concurrently` для параллельного запуска dev-серверов.

`packages/shared` собирается `tsc` в `dist` с декларациями и подключается как обычная
зависимость workspace (`"@kim/shared": "workspace:*"`). Это надёжнее, чем подключать
TypeScript-исходники через path mapping: один и тот же способ работает и в сборке Nest,
и в Vite, и в тестах, без дублирования алиасов в трёх конфигах. Цена — пакет надо
собрать до старта приложений, поэтому `dev` сначала собирает `shared`, а затем держит его
в watch-режиме.

### Офлайн-стратегия для экзамена

Основной путь (pnpm-нативный):

1. Заранее на машине с интернетом: `pnpm install`, затем `pnpm store path` и копирование
   хранилища вместе с `pnpm-lock.yaml` на носитель/в публичную папку сервера.
2. На экзамене: `pnpm config set store-dir <путь к копии>` и
   `pnpm install --offline --frozen-lockfile`.

План отхода, если копировать store нельзя и нужен переносимый `node_modules`: добавить в
`.npmrc` строку `node-linker=hoisted`, выполнить `pnpm install` на машине с интернетом и
переносить каталог `node_modules` целиком. Строгая изоляция при этом теряется, но проект
разворачивается копированием.

Оба пути обязательно прогоняются в Части 7 с физически отключённой сетью. До этого
`node-linker` оставляем по умолчанию, чтобы ловить незаявленные зависимости на этапе
разработки.

## Проверено на практике (16.10.2026)

При первом развёртывании каркаса вылезли три вещи, которые на экзамене стоили бы времени:

1. **corepack должен быть версии 0.36+.** pnpm 12 переехал на нативный бинарник, и его
   точка входа теперь `bin/pnpm.mjs`, а не `bin/pnpm.cjs`. corepack 0.34 (тот, что идёт
   с Node 24.11) падает с `MODULE_NOT_FOUND`. Лечится так:

   ```bash
   npm install -g corepack@latest
   rm -rf ~/.cache/node/corepack/v1/pnpm/<версия>   # дескриптор кэшируется испорченным
   ```

2. **`corepack pnpm <cmd>` не годится для вложенных вызовов.** Корневые скрипты вызывают
   `pnpm --filter ...`; дочерний `pnpm` берётся из PATH, не совпадает с версией из
   `packageManager` и падает с `ERR_PNPM_BAD_PM_VERSION` — pnpm не переключает версию,
   когда запущен из-под corepack. Поэтому **рабочий способ — вызывать `pnpm` напрямую**:
   начиная с 10-й версии он сам читает `packageManager` и скачивает нужную версию.
   corepack оставляем как способ поднять pnpm на машине, где его нет вообще.

3. **Настройка разрешённых postinstall-скриптов живёт в `pnpm-workspace.yaml` и
   называется `allowBuilds`.** В pnpm 10 это был `onlyBuiltDependencies` (список), в
   pnpm 11+ — `allowBuilds` (отображение `пакет: true`). Старое имя молча игнорируется, а
   поле `pnpm` в `package.json` больше не читается вовсе. Без этого не ставится `lefthook`
   (см. ADR-0010).

Вывод для Части 7: в офлайн-чеклист попадают не только пакеты, но и **версия corepack**
и **синтаксис `allowBuilds`** — иначе установка на площадке встанет на ровном месте.

## Последствия

- Положительные: правила валидации из ТЗ живут в одном месте и используются обеими
  сторонами; один `pnpm install`, один линтер, один форматтер; версия менеджера пакетов
  одинакова у всех и на площадке.
- Отрицательные / принятый долг: `packages/shared` нужно собирать перед запуском;
  симлинковый `node_modules` требует отдельной офлайн-процедуры.
- **Что это требует на экзамене:** на машине должен быть Node 20+ и либо включённый
  corepack, либо заранее положенный рядом pnpm; подготовленное хранилище pnpm; прогнанная
  и записанная в README последовательность команд развёртывания.

## Связанные критерии КИМ

- Разработка подсистем безопасности ИС (единая валидация фронт/бэк) — 16 б.
- Оформление кода в соответствии со стандартом кодирования (единый ESLint/Prettier на
  весь репозиторий) — Задание 3.
