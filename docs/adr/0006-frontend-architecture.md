# ADR-0006: Архитектура фронтенда и паттерны Effector

- **Статус:** принято
- **Дата:** 2026-10-19
- **Часть плана:** Часть 3. Frontend: каркас

## Контекст

Фронтенд отвечает за два критерия: «Разработка интерфейса пользователя веб-приложений в
соответствии с техническим заданием» — **15 баллов**, и «оформлять код программы в
соответствии со стандартом кодирования» (Задание 3). Страниц пять: регистрация,
авторизация, просмотр заявок, формирование заявки, панель администратора.

Ограничения: 1 ч 30 мин на всё Задание 1 вместе с базой и бэкендом; нет интернета, то
есть каждая зависимость должна лежать в офлайн-хранилище, а документация — в репозитории.

Выбранный стек — Effector. Принцип, под который он берётся: **UI тупой, бизнес-логика
декларативная**. Если логика расползётся по `useEffect`, Effector превратится в дорогой
способ хранить состояние, и смысла в нём не будет.

## Решение 1: структура — Feature-Sliced Design, но урезанный

Используем слои `app`, `pages`, `entities`, `shared`. Слой `features` вводим **только
когда появится настоящий срез** (например, «оставить отзыв»), `widgets` пока не
используем вообще.

Почему не полный FSD со всеми шестью слоями: на пять страниц это церемония, которая под
таймером съедает время и порождает папки с одним файлом. Почему не плоская структура:
критерий Задания 3 прямо требует стандарта кодирования, а FSD — проверяемый стандарт с
понятным правилом импортов (слой знает только о слоях ниже).

```
src/
  app/        провайдеры, тема, запуск приложения, роутер
  pages/      по странице из ТЗ, только композиция
  entities/   session, application, room — модели и отображение сущностей
  shared/     api-клиент, библиотека валидации форм, UI-примитивы, конфиг роутов
```

Правило импортов: `app → pages → entities → shared`, в обратную сторону — никогда.
Каждый слайс отдаёт наружу только то, что объявил в своём `index.ts`.

## Решение 2: роутинг — `@effector/router`

|                                  | `@effector/router` 1.2                             | react-router 7/8                        |
| -------------------------------- | -------------------------------------------------- | --------------------------------------- |
| Роут как единица Effector        | **да**                                             | нет                                     |
| Загрузка данных при открытии     | `sample({ clock: route.opened, target: fetchFx })` | `useEffect` или загрузчики вне Effector |
| Распространённость, документация | меньше                                             | больше                                  |

Выбран **`@effector/router`** (документация — https://router.effector.dev). Решающий
довод: открытие роута — это событие Effector, поэтому загрузка данных страницы
описывается декларативно, рядом с остальной логикой, без `useEffect`. Это ровно то, за чем
берётся Effector; с react-router пришлось бы склеивать два мира императивно.

### Поправка, которую стоит запомнить

Сначала я поставил **`atomic-router` 0.12.0** — именно он находится в npm по запросу
«effector router» и выглядит как актуальный пакет. На самом деле это **прежнее имя**
библиотеки: развитие продолжается под `@effector/router`, текущая версия 1.2.0 от
19.07.2026, и API у неё другой — `createRouter` вместо `createHistoryRouter`, путь
задаётся в `createRoute({ path })`, история подключается через `historyAdapter`.

Вывод на будущее: **версию библиотеки сверяем с её сайтом документации, а не с выдачей npm
по созвучному имени.** На экзамене такая ошибка стоила бы переписывания уже работающего
кода.

### Цена решения

`@effector/router` требует больше peer-зависимостей, чем прежняя версия: `effector-action`,
`patronum`, `query-string`, `zod` и `history`. Все — чистый JS без нативных сборок, то есть
офлайн-установке не мешают, но в хранилище их надо положить.

Документацию вендорим в репозиторий, как и для Mantine: `pnpm router:docs`. Сайт на
VitePress и не отдаёт ни `llms.txt`, ни исходный markdown, а в репозитории библиотеки
разметки документации нет — поэтому скрипт скачивает страницы и переводит их в текст:
23 страницы, 176 КБ, ищется `grep`-ом.

Если на экзамене роутер подведёт, откат на `react-router-dom` затрагивает только
`app/router` и `shared/routes` — страницы о роутинге не знают.

Защищённые маршруты сделаны обычными `sample`-переходами в `app/bootstrap.ts`, а не через
`chainRoute`: проверка сессии у нас одна на всё приложение, и отдельная цепочка на каждый
роут была бы сложнее без выигрыша.

Важная тонкость, на которой я сначала ошибся: **проверка сессии асинхронная**. Если
закрывать защищённый роут сразу по `$isAuthenticated`, то при первой загрузке страницы
пользователя с действующей cookie выбросит на вход — запрос `GET /auth/me` просто не
успеет завершиться. Поэтому переход на вход происходит только когда сессия уже проверена
(`$sessionChecked`), и отдельно — по завершении проверки, если открыт защищённый роут.

При этом **доступ всё равно проверяет сервер** (ADR-0004): клиентская проверка здесь
только для того, чтобы не показывать заведомо недоступный экран.

## Решение 3: работа с сервером — свои эффекты, без Farfetched

Farfetched даёт кэш, повторные попытки, контракты и барьеры авторизации. Для восьми
эндпоинтов это больше понятий, чем пользы: ещё одна зависимость в офлайн-хранилище и ещё
один слой, который надо держать в голове под таймером.

Берём тонкий `shared/api` плюс обычные `createEffect`. Это осознанный выбор «меньше
машинерии», а не незнание альтернативы: если приложение вырастет за пределы ДЭ, Farfetched —
естественный следующий шаг, и переход затронет только модели сущностей.

### Пересмотр решения с замерами (19.10.2026)

Решение перепроверено, когда страницы были уже написаны. Чтобы не спорить на ощущениях,
обращения к сети посчитаны протоколом браузера:

| Сценарий                                   | Было                             | Стало |
| ------------------------------------------ | -------------------------------- | ----- |
| Ввод девяти символов в фильтр «Заявитель»  | 9                                | **1** |
| Шесть переходов между страницами (кликами) | 6 загрузок справочника помещений | **1** |

Оба дефекта настоящие, и оба Farfetched действительно закрыл бы — задержкой и кэшем. Но
закрылись они **без новой зависимости**:

- задержка — `debounce` из `patronum`, который уже стоит как peer-зависимость
  `@effector/router`;
- однократная загрузка справочника — `filter` в `sample` по признаку «справочник пуст».

Итог: на восьми эндпоинтах Farfetched не окупается. Его понятия — query, mutation,
контракты, барьеры — это заметный объём того, что надо держать в голове под таймером,
а конкретную пользу мы получили двумя строками. Плюс сам пакет всё ещё в версии 0.x
(0.15.0) при 2068 загрузках в неделю.

Отдельный вывод на будущее: **первый замер был неверным**. Переходы делались полной
перезагрузкой страницы, при которой Scope пересоздаётся и кэш обнуляется по определению —
цифры показывали шесть запросов и после правки. Правильный замер ходит по приложению
кликами, как живой пользователь.

Что обязательно должно быть в api-клиенте:

- `credentials: 'include'` — сессия живёт в httpOnly-cookie (ADR-0004);
- относительный `/api`, никаких абсолютных адресов: одна и та же сборка работает локально
  через прокси Vite и за общим сервером на площадке;
- разбор ответа `ApiErrorResponse` в типизированную `ApiError`, у которой есть
  `fieldErrors` — именно её формы раскладывают по полям (ADR-0005);
- 401 превращается в событие «сессия закончилась», на которое реагирует модель сессии, а
  не каждый вызов по отдельности.

## Паттерны Effector, которых держимся

1. **Компонент не содержит логики.** Только `useUnit` и разметка. Любое «если» про
   бизнес-правило — в модели.
2. **Связи через `sample`**, а не вызовы эффектов из обработчиков событий React. Исключение —
   отправка формы, где событие приходит из DOM.
3. **Загрузка данных привязана к `route.opened`**, а не к монтированию компонента.
4. **Состояние запроса не хранится вручную**: `$pending` берётся из `effect.pending`,
   ошибка — из `effect.failData`.
5. **Никакого `localStorage` для сессии.** Признак «вошёл» — результат `GET /api/auth/me`.
   Токен в httpOnly-cookie браузер отправляет сам, и читать его из JS нельзя по замыслу.
6. Запуск приложения — явный: событие `appStarted` в `app`, от него `sample` к
   `fetchSessionFx`.
7. **Императивный запуск юнита — только через `allSettled` со Scope**, а внутри React —
   только через `useUnit`. Прямой вызов обновил бы глобальное состояние вместо того,
   которое видит интерфейс.

## Решение 5: приложение работает в Scope

Юниты Effector по умолчанию держат состояние в себе, на уровне модуля. Приложение вместо
этого создаёт изолированный **Scope** через `fork()` и оборачивается в `Provider` из
`effector-react` (`app/scope.ts`, `app/index.tsx`).

Зачем это на клиенте, где глобальных юнитов хватило бы:

1. **Тесты идут тем же путём, что браузер.** Они и так используют `fork` и `allSettled`;
   теперь это не «тестовый режим», а то, как приложение работает всегда.
2. **Целый класс ошибок перестаёт существовать.** С включённой конфигурацией `scope` в
   `eslint-plugin-effector` прямой вызов юнита вне `useUnit`/`allSettled` становится
   ошибкой линтера. Иначе такой вызов меняет глобальное состояние, а интерфейс читает
   состояние Scope — расхождение, которое проявляется не сразу.
3. **Дорога к SSR открыта**: если понадобится, добавляется только сериализация.

Порядок инициализации важен и задан документацией роутера:

```ts
const scope = fork();
await allSettled(router.setHistory, { scope, params: historyAdapter(createBrowserHistory()) });
await allSettled(appStarted, { scope });
// только теперь рендерим
```

История подключается первой: до неё `router.navigate` отвечает `navigationFailed` с
причиной `not-initialized`. Проверка сессии тоже дожидается завершения до первого рендера —
это один запрос к своему же API, зато пользователь с действующей cookie не видит вспышку
формы входа перед переходом на свои заявки.

Цена: любой императивный запуск юнита идёт через `allSettled`, а не вызовом. Плагин babel
или swc для Effector **не подключаем**: sid-ы нужны для сериализации состояния (SSR), а
для клиентского `fork` без неё они не требуются — лишняя зависимость в офлайн-хранилище.

## Уточнения, принятые в Части 5

### HTTP-клиент — `ofetch`

Свой `request()` на `fetch` заменён на [ofetch](https://github.com/unjs/ofetch). Что это
дало: разбор JSON и сборку строки запроса из коробки, перехватчик `onResponseError` —
реакция на 401 описана один раз, а не в каждом вызове, и ошибки приходят объектом
`FetchError` с уже разобранным телом.

Клиентов два, и это не случайность: у основного перехватчик превращает 401 в
«сессия закончилась», а у второго его нет. Второй нужен ровно для `GET /auth/me`, где
401 — нормальный ответ «не вошёл». Через общий клиент гость на странице регистрации
получал бы переход на вход при каждой загрузке.

Цена: одна зависимость (сама `ofetch` плюс три её собственные — `destr`,
`node-fetch-native`, `ufo`). Все небольшие и без нативных сборок, офлайн-установке не
мешают.

### Тесты фронтенда — `vitest` с `happy-dom`

Встроенный раннер Node заменён на vitest. Причина не в удобстве: `node --test` не умеет
рендерить компоненты, а Задание 2 требует, чтобы **ошибки валидации отображались на
форме** — это проверяется только рендером. Теперь есть и то и другое: модели проверяются
через `fork` и `allSettled`, формы — через `@testing-library/react`.

`happy-dom`, а не `jsdom`: заметно быстрее, возможностей хватает. Чего в нём нет и что
добивается в `src/test/setup.ts` — `matchMedia` (иначе падают компоненты с
`visibleFrom`/`hiddenFrom`) и `ResizeObserver` (иначе падают `Select` и `Modal`).

Цена: шесть зависимостей разработки вместо нуля. Для офлайн-хранилища это заметно, но
проверка требования ТЗ того стоит. Бэкенд при этом остаётся на встроенном раннере Node —
там рендерить нечего.

### Состояние списка — размеченное объединение, сопоставление через `ts-pattern`

Страницы со списками рисовали четыре независимых условия: загрузка, ошибка, пустота и
данные. Это давало две проблемы. Во-первых, возможны невозможные сочетания — идёт
загрузка и одновременно показана ошибка. Во-вторых, решающая логика вида
`pending && items.length === 0` и `isEmpty && !loadError` жила **в компоненте**, прямо
вопреки правилу 1 из этого же ADR.

Теперь состояние считается в модели одним значением:

```ts
type ListViewState<T> =
  | { kind: 'loading' }
  | { kind: 'error'; message: string }
  | { kind: 'empty' }
  | { kind: 'list'; items: T[] };
```

Компонент сопоставляет вариант с разметкой через `match(...).exhaustive()`. Побочная
выгода: функция `toListViewState` чистая, и её поведение покрыто тестами — раньше эта
логика была размазана по JSX и не тестировалась вовсе. Там же зафиксировано правило
«данные показываем даже во время обновления», чтобы список не мигал загрузчиком при смене
фильтров.

Почему именно `ts-pattern`, а не `switch` с `assertNever`: главный выигрыш даёт само
объединение, и его можно было получить бесплатно. Но `switch` внутри JSX требует
вспомогательной функции или немедленно вызываемого выражения, и читается хуже. Замер
показал, что цена невелика: сборка выросла с 599.79 КБ до 605.20 КБ, в gzip —
со 187.44 КБ до 189.05 КБ, то есть **+1.6 КБ**. Библиотека без зависимостей, MIT, с
`sideEffects: false`.

Отдельно про отвергнутый вариант: рассматривался `@diegogbrisa/ts-match` — 47 загрузок в
неделю против 3.8 миллиона у `ts-pattern`. Для проекта, где каждая зависимость едет в
офлайн-хранилище на площадку, непроверенный пакет — лишний риск без выигрыша.

### Правила навигации — `createAction`, а не семь `sample`

Решение «где сейчас должен быть пользователь» было размазано по семи `sample` с
`combine` и `filter`: защита маршрутов, возврат вошедшего со страницы входа, переход
после успешного входа, корень, панель администратора, выход, протухшая сессия. Правило
приходилось собирать в голове из кусков, и один кусок я уже однажды забыл — после входа
пользователь оставался на форме.

Теперь это одна функция в `createAction` из
[effector-action](https://github.com/AlexeyDuybo/effector-action): источники и цели
объявлены явно, а внутри обычные условия, которые читаются сверху вниз.

Библиотека выбрана не по числу загрузок: `createAction` **официально рекомендован в
руководстве Effector** и [переезжает в ядро в следующем мажоре](https://github.com/effector/effector/issues/1275).
К тому же она уже была в дереве зависимостей как peer `@effector/router` — то есть
обошлась бесплатно.

### Модель как фабрика: `createModel`

Юниты объявлялись на уровне модуля, и публичной границы у модели не было: любой `export`
сразу становился частью интерфейса. Теперь модель — фабрика, а наружу отдаётся только то,
что перечислено в `return`, с разделением по потребителю: `viewModel` для компонента, `__`
для тестов, остальные поля — для связи между моделями.

Сам помощник тривиален (`<T>(factory: () => T) => factory()`), ценность в соглашении.
Выигрыш проявился сразу: страницы перестали импортировать внутренние сторы, а компонент
теперь читается одной строкой — `useUnit(Model.viewModel)`, потому что `viewModel` это и
есть готовая форма для `useUnit`.

Отвергнут [effector-use-unit-shape](https://github.com/AlexeyDuybo/effector-use-unit-shape):
он даёт подписку только на использованные поля через Proxy, но это версия 0.1.0 при трёх
загрузках в неделю. Для офлайн-хранилища на площадке ДЭ непроверенный пакет — лишний риск,
а выигрыш от точечных подписок на страницах такого размера незаметен.

### `useUnit` в объектной форме, без `@effector/reflect`

Рассматривался [@effector/reflect](https://reflect.effector.dev) — он связывает юниты с
компонентами декларативно, снаружи, и доводит принцип «UI тупой» до предела.

Библиотека хорошая и официальная (MIT, без зависимостей), но её сильная сторона —
**листовые компоненты, привязанные к юнитам напрямую**: поле ввода, у которого `value` и
`onChange` связаны со стором и событием. У нас такого нет: формы работают через
`@mantine/form` с локальным состоянием, а в Effector уходит только отправка (ADR-0007).

Боль, которую reflect снял бы у нас, была другой — длинные **позиционные** вызовы:

```ts
const [a, b, c, d, e, f, g] = useUnit([$a, $b, $c, d, e, f, g]);
```

Два списка приходится держать в одном порядке руками, и перестановка строки молча
подменяет значения местами. Но это лечится без новой зависимости: `useUnit` принимает
объект и возвращает объект.

```ts
const { user, isAdmin, logout } = useUnit({
  user: $user,
  isAdmin: $isAdmin,
  logout: logoutRequested,
});
```

Переведены все страницы и общий каркас. Связь имени с юнитом стала явной, позиционной
ошибки больше не существует как класса. К reflect вернёмся, если появятся компоненты,
привязанные к юнитам напрямую.

### Типы DTO сужены до объединений

`status`, `paymentMethod`, `kind` и `role` в `@kim/shared` были `string`, стали
объединениями из домена. Это убрало охранные функции на фронтенде и дало исчерпывающую
проверку бесплатно: `Record<ApplicationStatus, …>` в `StatusBadge` перестанет
компилироваться, если в ТЗ появится четвёртый статус.

## Проверка кода: eslint-plugin-effector

Подключён [eslint-plugin-effector](https://eslint.effector.dev) — конфигурации
`recommended`, `react` и `patronum`. Из-за него для фронтенда включён типизированный
линтинг: часть правил опирается на типы.

Конфигурацию `scope` не включаем: `fork` используется только в тестах, в приложении Scope
не применяется, и правила требовали бы передавать scope там, где его нет.

Плагин сразу нашёл настоящую ошибку в первом варианте каркаса: `routes.X.open()`
вызывался прямо в компонентах, минуя привязку к scope. Правильный вид —
`useUnit(routes.X.open)`. Без `fork` это не ломает приложение, но проявляется при SSR и в
тестах со scope — то есть там, где искать дороже всего. Там же выяснилось, что в тестах
`.watch` на юните не привязан к scope: заменено на `createWatch({ unit, scope, fn })`.

## Сквозные проверки в браузере

Модульные тесты проверяют модели, запросы `curl` — API. Между ними остаётся то, что
ломается чаще всего: формы, переходы и защита маршрутов. Для этого в `scripts/` лежит
свой драйвер Chrome через DevTools Protocol и набор проверок (`pnpm e2e`).

Почему не Playwright: он тянет собственные сборки браузеров на сотни мегабайт, которые
пришлось бы класть в офлайн-хранилище. Здесь используется уже установленный Chrome, а
`WebSocket` встроен в Node 22+ — **ноль новых зависимостей**.

Проверки сразу нашли два настоящих дефекта, которых не видели ни модульные тесты, ни
запросы к API:

1. **После успешного входа пользователь оставался на форме входа.** В переходе на свои
   заявки не было событий `loginFx.doneData` и `registerFx.doneData` — только
   `fetchSessionFx.doneData`. То есть вход работал, но никуда не вёл.
2. **`Badge` в Mantine приводит текст к верхнему регистру**, и логин администратора из ТЗ
   `Conf2027` отрисовывался как `CONF2027`. Логины регистрозависимы, поэтому в шапке
   теперь подпись роли, а не логин.

Запуск требует поднятого стека (`pnpm dev`), поэтому в git-хуки эти проверки не
добавлены — в `pre-push` остаётся только `typecheck`.

В Части 4 набор дополнен сквозным сценарием Задания 1 целиком: регистрация нового
пользователя, формирование заявки выпадающими списками, фильтрация у администратора,
смена статуса, отзыв и запрет второго отзыва. Логин в сценарии уникален для каждого
запуска, поэтому проверки можно гонять подряд; накопившиеся данные чистятся
`pnpm db:reset` с последующими `db:migrate` и `db:seed`.

## Последствия

- Положительные: логика страницы читается в одном файле модели; загрузка данных не зависит
  от жизненного цикла React; откат роутинга и переход на Farfetched локализованы.
- Отрицательные / принятый долг: `@effector/router` менее распространён — меньше примеров
  под рукой, и он притащил пять peer-зависимостей; без Farfetched нет кэша и повторных
  попыток, каждый экран грузит данные заново.
- **Что это требует на экзамене:** отрепетировать цепочку «роут открылся → эффект → стор →
  компонент»; помнить, что `credentials: 'include'` обязателен, иначе cookie не уедет и всё
  выглядит как «авторизация не работает»; помнить, что проверка сессии асинхронная —
  защищённый роут нельзя закрывать до её завершения, иначе пользователя с действующей
  cookie выбросит на вход при первой загрузке.
