# Порядок работы на экзамене

Пошаговый план: что делать, в каком порядке, чем проверять и когда коммитить. Рассчитан
на ГИА ДЭ БУ — три задания, 3 ч 30 мин. Для ПА берётся только Задание 1 (1 ч 30 мин).

Главное правило: **каждый шаг заканчивается проверкой**. Не «написал и пошёл дальше», а
«написал, увидел, что работает, пошёл дальше». Ошибка, найденная через сорок минут, стоит
втрое дороже найденной сразу.

---

## Подготовительный день

В день экзамена этого уже не сделать, поэтому список короткий и обязательный.

- [ ] Проверить, что на машине есть **Node 20.19+**: `node -v`. Если нет — работаем по
      плану отхода, см. [запасной бэкенд](../apps/backend-py/README.md).
- [ ] Проверить **СУБД**: PostgreSQL или MySQL, по [docs/db-setup.md](./db-setup.md).
      Выяснить порт и то, кто на нём слушает: `lsof -nP -iTCP:5432 -sTCP:LISTEN`.
- [ ] Поставить зависимости **офлайн** и убедиться, что это работает: отключить сеть и
      выполнить `pnpm install --offline --frozen-lockfile`.
- [ ] Проверить, есть ли **pnpm**: `pnpm -v`. Если нет — см. раздел «Если на машине нет
      pnpm» ниже; лучше прогнать переключение заранее, а не в день экзамена.
- [ ] Проверить, что база поднимается и миграции проходят: `pnpm --filter @kim/backend db:migrate`.
- [ ] Скачать полный офлайн-справочник: `pnpm mantine:docs:full`, `pnpm router:docs`.
- [ ] Проверить, что **ER-диаграмма строится в СУБД** — открыть DBeaver или pgAdmin и
      сделать это руками один раз, чтобы в день экзамена не искать пункт меню.
- [ ] Решить, в каком режиме работаем со схемой (см. следующий раздел) и записать в `.env`.

## Если на машине нет pnpm

В перечне ПО из КИМ pnpm нет. Хорошая новость: **npm идёт в комплекте с Node**, поэтому
если Node есть, запасной путь доступен всегда — ставить ничего не нужно.

Что мешает npm в нашем репозитории и почему это не решается одной командой:

1. Состав воркспейсов объявлен в `pnpm-workspace.yaml`, которого npm не читает.
2. Зависимость на общий пакет записана как `workspace:*` — это протокол pnpm.
3. Корневые скрипты вызывают сам `pnpm`.

Всё три правятся одной командой:

```bash
node scripts/npm-fallback.mjs
rm -rf node_modules apps/*/node_modules packages/*/node_modules
npm install
```

Дальше всё работает как обычно, только через `npm run`: `npm run dev`, `npm run build`,
`npm test`. Вернуться обратно: `node scripts/npm-fallback.mjs --revert`.

**Проверено:** на копии репозитория `npm install` и `npm run build` проходят, сборка
получается того же размера.

### Самый надёжный путь: не ставить ничего

Если есть возможность подготовиться заранее, лучший вариант — **привезти `node_modules`
готовым**. Тогда не нужен ни pnpm, ни npm, ни сеть.

Для этого в `.npmrc` раскомментировать `node-linker=hoisted` и выполнить `pnpm install` на
машине с интернетом: каталог станет обычными файлами вместо символических ссылок и будет
переноситься копированием. Подробности — в
[ADR-0002](./adr/0002-monorepo-and-package-manager.md).

## Про миграции: на экзамене они не нужны

КИМ требует спроектировать базу и сохранить **ER-диаграмму, построенную в СУБД**. Про
миграции в задании нет ни слова — оценивается результат в базе, а не способ, которым он
туда попал.

Поэтому на экзамене работаем в режиме автоматической синхронизации:

```bash
echo 'DB_SYNCHRONIZE=true' >> .env
```

Дальше цикл такой: правим сущность → перезапускаем бэкенд → таблица уже изменилась. Без
`build`, `migration:generate` и `migration:run`, которые в сумме съедают около полминуты
на каждую правку схемы, а правок за полтора часа набирается десяток.

Чем платим: изменение типа столбца может потерять данные, и истории схемы не остаётся. На
экзамене с демонстрационными данными это терпимо.

**Если в конце останется время**, можно вернуть `DB_SYNCHRONIZE=false` и одной командой
получить миграцию — `pnpm --filter @kim/backend db:migrate:generate FinalSchema`. Это
приятное дополнение, а не требование.

## Задание 1 — 1 ч 30 мин

Порядок не случайный: он выстроен так, чтобы **каждый следующий шаг можно было проверить
предыдущим**, и чтобы самое дорогое по баллам (подсистема безопасности, 16 б.) было
сделано раньше, чем кончится время.

### Шаг 0. Развернуть каркас — 5 минут

```bash
cp .env.example .env            # и вписать JWT_SECRET: openssl rand -base64 48
echo 'DB_SYNCHRONIZE=true' >> .env
pnpm install                    # офлайн: pnpm install --offline --frozen-lockfile
pnpm db:up                      # или локальная СУБД, см. docs/db-setup.md
```

**Проверка:** `pnpm dev` поднимается без ошибок, `curl localhost:3000/api/health` отвечает.

**Коммит:** `chore: развернуть каркас` — КИМ требует коммит в начале задания.

### Шаг 1. Сущности и база — 20 минут

Пишем сразу четыре сущности, не по одной: они связаны, и проверять их поодиночке незачем.

| Сущность       | Что не забыть                                                          |
| -------------- | ---------------------------------------------------------------------- |
| `users`        | **уникален только логин**; email уникальным не делать — ТЗ не требует  |
| `rooms`        | отдельная таблица, а не строка в заявке: в Задании 2 нужен список      |
| `applications` | статус по умолчанию «Новая», `starts_at` со временем, а не только дата |
| `reviews`      | один отзыв на заявку — `UNIQUE` на `application_id`                    |

Все значения статусов, способов оплаты и типов помещений берутся из
`packages/shared/src/domain.ts` — **дословно из ТЗ**, не переформулировать.

**Проверка:**

```bash
pnpm --filter @kim/backend db:seed   # справочник и администратор Conf2027/Demo77
pnpm --filter @kim/backend db:schema:log   # должно быть «schema is up to date»
```

### Шаг 2. ER-диаграмма — 5 минут

Это **требование задания**, и его легко забыть в спешке. Делаем сразу, пока схема свежая.

1. Открыть DBeaver → подключение → схема `public` → правый клик → **Просмотр диаграммы**.
2. Экспортировать в PNG → положить в `docs/er/`.

Мышкой — потому что это работает на любой машине. Если на площадке вдруг окажется
graphviz, то же самое делает `pnpm erd`, но проверять его наличие в экзаменационное
время не стоит.

Подробности и альтернативы (pgAdmin, MySQL Workbench) — в [docs/er](./er/README.md).

**Коммит:** `feat(db): схема данных и ER-диаграмма`.

### Шаг 3. Безопасность — 20 минут

Самый дорогой критерий, 16 баллов. Делается до всего остального интерфейса.

- регистрация со всеми пятью правилами из ТЗ;
- вход с **одинаковым сообщением** при неверном пароле и несуществующем логине;
- выход;
- `GET /auth/me`;
- роли и защита маршрутов: пользователь видит только свои заявки.

Правила валидации не писать руками — импортировать из `@kim/shared`.

**Проверка** (быстрее, чем через браузер):

```bash
curl -s -X POST localhost:3000/api/auth/register -H 'Content-Type: application/json' \
  -d '{"login":"ab","password":"123","fullName":"Ivanov","phone":"89991234567","email":"нет"}'
# ожидаем 400 и пять сообщений по полям

curl -s -X POST localhost:3000/api/auth/login -H 'Content-Type: application/json' \
  -d '{"login":"Conf2027","password":"Demo77"}' -c /tmp/c.txt
curl -s -b /tmp/c.txt localhost:3000/api/auth/me
```

### Шаг 4. Заявки, отзывы, админка — 15 минут

- создание заявки, список «мои»;
- отзыв только по завершённому мероприятию и только автором;
- список всех заявок и смена статуса — **только для роли admin**.

**Проверка:** те же `curl`. Отдельно проверить, что обычный пользователь получает 403 на
админском пути — это прямой пункт критерия.

**Коммит:** `feat(api): аутентификация и заявки`.

### Шаг 5. Пять страниц — 20 минут

Порядок: вход → регистрация → мои заявки → новая заявка → админка. Именно в этом порядке:
без входа остальное не проверить.

Тексты, которые эксперт сверяет буквально:

- ссылка «Еще не зарегистрированы? Регистрация» и обратный переход;
- кнопка «Создать пользователя»;
- кнопка «Отправить» в форме заявки;
- статусы «Новая», «Мероприятие назначено», «Завершено»;
- способы оплаты «При очном посещении», «Переводом по системе СБП».

**Проверка:** пройти сценарий руками в браузере — регистрация, заявка, вход
администратором, смена статуса, отзыв. Либо автоматически, если стек поднят: `pnpm e2e`.

### Шаг 6. Финал — 5 минут

- [ ] ER-диаграмма лежит в рабочей папке.
- [ ] Коммит в конце задания — это требование КИМ.
- [ ] Всё запушено в индивидуальный репозиторий.

## Задание 2 — 1 ч 00 мин

Дизайн. 25 баллов, из них 11 — за соответствие **корпоративному стилю заказчика**.

### Шаг 1. Стиль заказчика — 10 минут

Открыть «Руководство по стилю» из приложения к заданию и перенести значения в тему **как
есть**: пять цветов, PT Sans, размеры 36/24/18/16/12. Не подбирать похожие из палитры
библиотеки — разницу видно пипеткой.

Шрифт подключить **локально из файлов** приложения: Google Fonts на площадке недоступны,
и внешний шрифт просто не загрузится.

Готовая тема — в `apps/frontend/src/shared/theme/`, разбор — в
[ADR-0007](./adr/0007-mantine-theme-and-forms.md) и [ADR-0008](./adr/0008-design-concept.md).

### Шаг 2. Изображения — 15 минут

```bash
# положить отобранные файлы в assets/source/rooms, затем
pnpm images
```

Конвейер кадрирует, уменьшает и сохраняет в AVIF, WebP и JPEG в двух размерах. Это прямо
закрывает формулировку «оптимизировать и улучшить».

### Шаг 3. Мобильный макет 390×844 — 20 минут

Собирать **от узкого экрана**, а не наоборот. Проверять не размером окна браузера, а
эмуляцией устройства: окно Chrome не становится уже примерно 500 px.

```bash
E2E_WIDTH=390 E2E_HEIGHT=844 pnpm e2e
```

### Шаг 4. Дополнительный функционал — 15 минут

- ошибки валидации **на форме** (не в всплывающем окне);
- выпадающие списки вместо ручного ввода помещения и способа оплаты;
- отзыв доступен только после завершения мероприятия;
- фильтры и карточки в панели администратора.

**Коммит** в начале и в конце задания.

## Задание 3 — 1 ч 00 мин

### Шаг 1. Доработка базы — 10 минут

Пройтись по заданиям 1 и 2 и проверить, что схема покрывает всё: изображения помещений,
оценка в отзыве, индексы под фильтры.

### Шаг 2. Анимации — 20 минут

Правило: анимация **объясняет изменение**, а не развлекает. Появление карточек, отклик на
наведение, переходы состояний кнопок. Длительности 120–200 мс.

Обязательно уважить системную настройку «уменьшить движение» — это доступность, а не
вкус. Как сделано у нас — [ADR-0009](./adr/0009-performance-and-motion.md).

### Шаг 3. Производительность — 20 минут

- разделение сборки по страницам;
- индексы под фильтры, которые реально используются;
- убрать запрос на каждое нажатие клавиши в фильтрах.

**Мерить, а не предполагать.** У нас для этого есть журнал сетевых запросов в
`scripts/browser.mjs` и `EXPLAIN ANALYZE` для базы.

### Шаг 4. Качество кода — 10 минут

```bash
pnpm lint && pnpm format && pnpm typecheck && pnpm test
```

Критерий Задания 3 прямо говорит про «стандарт кодирования» — линт без ошибок это и есть
подтверждение.

## Если что-то пошло не так

| Симптом                                          | Что делать                                                                             |
| ------------------------------------------------ | -------------------------------------------------------------------------------------- |
| Нет Node.js на машине                            | Запасной бэкенд: [apps/backend-py](../apps/backend-py/README.md), фронтенд не меняется |
| Нет PostgreSQL, есть MySQL                       | Сменить `type` в `data-source.options.ts`, см. [docs/db-setup.md](./db-setup.md)       |
| `role "kim" does not exist` при живом контейнере | Локальная СУБД перехватила порт. `lsof -nP -iTCP:5432 -sTCP:LISTEN`                    |
| «Авторизация не работает»                        | Забыт `credentials: 'include'` в запросах либо `JWT_SECRET` в `.env`                   |
| Вход перестал пускать всех                       | Сработало ограничение частоты. `AUTH_THROTTLE_LIMIT=100` в `.env`                      |
| Git-хук не даёт закоммитить под таймером         | `LEFTHOOK=0 git commit -m "..."` — аварийный выход, не норма                           |
| Схема не меняется после правки сущности          | Не выставлен `DB_SYNCHRONIZE=true` либо бэкенд не перезапущен                          |
