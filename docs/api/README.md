# Контракт API

Описание существует не ради красивой страницы, а как **техзадание для второй реализации
бэкенда на Python/MySQL** (Часть 2Б плана). Фронтенд обращается к относительному `/api`,
поэтому любой бэкенд, реализующий этот контракт, подключается заменой прокси — переписывать
клиент не придётся.

## Где что лежит

| Что                         | Где                                   | Чем генерируется                      |
| --------------------------- | ------------------------------------- | ------------------------------------- |
| Пути, методы, тела запросов | [openapi.json](./openapi.json)        | `pnpm --filter @kim/backend api:spec` |
| Формы ответов               | `packages/shared/src/api.ts`          | написаны руками, общие с фронтендом   |
| Формат ошибок               | [ADR-0005](../adr/0005-validation.md) | —                                     |
| Правила валидации полей     | `packages/shared/src/validation.ts`   | —                                     |

Интерактивная страница при запущенном бэкенде: http://localhost:3000/api/docs
(отключается переменной `API_DOCS=false`).

## Честная оговорка про полноту

В `openapi.json` описаны **пути и тела запросов**, но не схемы ответов: плагин
`@nestjs/swagger` выводит схемы из классов, а наши ответы описаны TypeScript-интерфейсами
в `@kim/shared` — они общие с фронтендом, и дублировать их классами только ради
документации не хотелось.

Для Части 2Б это рабочий вариант: `ApplicationDto`, `RoomDto`, `ReviewDto`, `UserDto` и
`ApiErrorResponse` в `packages/shared/src/api.ts` читаются как спецификация. Если при
портировании выяснится, что этого мало, добавим классы ответов с `@ApiProperty` — это
отмечено в чеклисте Части 2Б.

## Что должна повторить вторая реализация

1. **Cookie-сессия.** httpOnly-cookie `conf_session` с подписанным токеном, `SameSite=Lax`,
   срок 7 дней. Детали и обоснование — [ADR-0004](../adr/0004-authentication.md).
2. **Единый формат ошибок** — `{ statusCode, message, errors?: { поле: сообщение } }`.
   Фронтенд раскладывает `errors` по полям формы; без этого ошибки валидации не
   отобразятся на форме, а это требование Задания 2.
3. **Формулировки сообщений дословно** из `packages/shared/src/validation.ts`. Эксперт
   сверяет текст с ТЗ.
4. **Правила, которые проверяются только на сервере** (перечислены в ADR-0005): уникальность
   логина, существование помещения, принадлежность заявки пользователю, допустимость
   перехода статуса, право на отзыв, отсутствие второго отзыва.
5. **Одинаковый ответ при неудачном входе** независимо от того, не найден логин или не
   совпал пароль.
6. **Отбрасывание незаявленных полей** в теле запроса (у нас это `whitelist` +
   `forbidNonWhitelisted`): попытка передать `role: "admin"` при регистрации должна
   приводить к ошибке, а не применяться частично.
