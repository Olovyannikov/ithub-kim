# Запасной бэкенд на Python/MySQL

План отхода на случай, если на площадке ДЭ не окажется Node.js. Обоснование и принятые
решения — [ADR-0011](../../docs/adr/0011-python-backend.md).

Реализует **тот же контракт**, что основной бэкенд на NestJS: те же пути, те же формы
ответов, тот же формат ошибок и та же сессия. Фронтенд переключается между ними заменой
адреса в прокси — **без единой правки в коде клиента**.

## Запуск

```bash
# 1. База (контейнер с MySQL 8.4)
docker compose --profile fallback up -d mysql

# 2. Окружение Python и зависимости
pnpm py:install

# 3. Схема и демонстрационные данные
pnpm py:seed

# 4. Сам бэкенд → http://localhost:3001/api
pnpm py:dev
```

Переключить фронтенд на него:

```bash
API_PROXY_TARGET=http://localhost:3001 pnpm dev:front
```

Проверить, что всё сошлось, можно теми же сквозными проверками, что и для основного
бэкенда: `pnpm e2e`. Все девять проходят без изменений в коде фронтенда — это и есть
доказательство, что контракт описан достаточно.

## Что совместимо с основным бэкендом

|                            | Как сделано                                                                                                                                   |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **Пароли**                 | Формат `scrypt$N$r$p$соль$хеш` разбирается встроенным `hashlib.scrypt`. Проверено в обе стороны: хеш от NestJS принимается Python и наоборот. |
| **Сессия**                 | Тот же токен HS256 в той же httpOnly-cookie `conf_session` с тем же `JWT_SECRET`.                                                             |
| **Ошибки**                 | Тот же формат `{ statusCode, message, errors }` — фронтенд раскладывает их по полям формы тем же кодом.                                       |
| **Тексты и правила из ТЗ** | Не дублируются, а **переносятся** скриптом `pnpm shared:python` из `packages/shared` в `app/shared_generated.py`.                             |

Последнее — главное. Две реализации одного API расходятся именно в формулировках, а их
эксперт сверяет с текстом КИМ дословно. Поэтому источник истины остаётся один.

## Чего здесь намеренно нет

- **Миграций.** Таблицы создаются из моделей при старте. Для основного бэкенда такой путь
  отвергнут (ADR-0003) — там нужна воспроизводимая история схемы. Здесь приоритет другой:
  запасной путь должен разворачиваться на чужой машине за минуты.
- **Индекса под поиск по заявителю.** Он был замерен и отвергнут ещё в основном бэкенде
  (ADR-0009): на нашем объёме данных не используется.

## Офлайн-установка

На площадке сети нет. Колёса готовятся заранее на машине с интернетом:

```bash
cd apps/backend-py
.venv/bin/python -m pip download -r requirements.txt -d wheels
```

Каталог `wheels` едет вместе с репозиторием, и `pnpm py:install` сам увидит его и поставит
без сети.

## Структура

```
app/
  main.py               приложение, обработчики ошибок, /api/health
  config.py             настройки из общего .env
  database.py           подключение к MySQL и модели (та же схема, что в docs/er)
  security.py           пароли на scrypt и токен сессии
  schemas.py            проверка тела запроса, правила из shared_generated
  serializers.py        формы ответов из контракта docs/api
  deps.py               сессия базы, текущий пользователь, роль, частота запросов
  routers/              auth, rooms, applications
  seed.py               справочник, администратор из ТЗ, демонстрационные заявки
  shared_generated.py   СГЕНЕРИРОВАН — pnpm shared:python
```
