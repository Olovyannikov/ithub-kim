# Конференции.РФ — подготовка к демонстрационному экзамену

Тренировочный проект по **КИМ 09.02.07-3-2027, Том 1 (инвариантная часть)**.
Специальность 09.02.07 «Информационные системы и программирование», квалификация
**«Разработчик веб и мультимедийных приложений»**.

Предметная область по заданию: портал **«Конференции.РФ»** — информационная система
бронирования помещений (аудитория, коворкинг, кинозал) для проведения Всероссийских
конференций.

### Функционал из задания

Задание 1 (минимально необходимый интерфейс, полный стек: фронтенд + бэкенд + БД + ООП + библиотеки/фреймворки):

1. **Регистрация.** Логин — уникальный, латиница и цифры, не менее 6 символов; пароль — минимум 8 символов; ФИО — кириллица и пробелы; телефон — формат `8(XXX)XXX-XX-XX`; email — формат электронной почты. Все поля обязательны. Кнопка «Создать пользователя» → запись в БД.
2. **Авторизация.** Ввод логина и пароля, сообщения при некорректном вводе. Переход «Еще не зарегистрированы? Регистрация» и обратно.
3. **Просмотр заявок.** Авторизованный пользователь видит свои заявки и может оставить отзыв о качестве проведённого мероприятия.
4. **Формирование заявки.** Помещение (ввод названия в поле), желаемая дата начала конференции (текстовое поле), способ оплаты: при очном посещении / переводом по СБП. Кнопка «Отправить» → заявка уходит администратору.
5. **Панель администратора.** Вход по логину `Conf2027` и паролю `Demo77`. Видны все заявки зарегистрированных пользователей. Статус изначально «Новая», администратор меняет на «Мероприятие назначено» или «Завершено».

Также: проектирование БД **с ER-диаграммой**, сохранённой в рабочей папке проекта в любом формате; коммиты минимум в начале и в конце выполнения задания.

Задание 2 (дополнительный функционал):

1. Регистрация: ошибки валидации отображаются **на форме**; по кнопке «Зарегистрироваться» пользователь заносится в базу, если валидация пройдена и логин уникален.
2. Авторизация: ошибки валидации отображаются на форме.
3. Личный кабинет: возможность оставить отзыв **только после завершения мероприятия**.
4. Формирование заявки: упростить заполнение — выбор опций из выпадающих списков; указание желаемой даты начала конференции.
5. Панель администратора: фильтрация заявок, отображение карточек заявок, улучшения дизайна.
6. Дизайн **всех** страниц под смартфон **390×844 px**; оптимизация и улучшение предоставленных изображений; допустимо представить дизайн в виде `.html` файлов (отдельный файл на страницу).

Задание 3:

1. Доработать БД так, чтобы она покрывала все задачи из предыдущих заданий.
2. Фреймворк/библиотеки для дружественного интерфейса и технологичности.
3. Адаптивный дизайн, качество кода (оформление по стандарту кодирования).
4. Анимации и микроанимации для улучшения UX.

### Условия проведения (важно для подготовки)

- **Интернета на рабочих местах участников нет.** Библиотеки и фреймворки заранее размещаются в публичной папке сервера; офлайн-справочник по технологиям — на рабочем месте.
- Общий сервер для БД, бэкенда, хранения и проверки работ, индивидуальных репозиториев.
- Медиафайлы (приложения к заданию) — в публичной папке сервера.
- Взаимодействие с БД участник проверяет в подготовительный день; в день экзамена проектирует БД самостоятельно.
- Из ПО по КИМ: ОС, FTP-менеджер, сервер (MySQL, PHP, SSH, SFTP, FTP, Python), SSH-клиент, офлайн-документация, браузеры, инструмент для API, **среда для выполнения JavaScript**, офисный пакет, растровый/векторный графические редакторы, инструмент прототипирования, IDE (Python / JS / редактор кода), **набор фреймворков — на усмотрение образовательной организации**.

> Приложение `Прил_1_ОЗ_КИМ_09.02.07-3-2027` получено. Внутри — **руководство по стилю

## 2. Стек

Зафиксирован в [ADR-0001](./docs/adr/0001-stack.md):

- **Backend:** NestJS 12, PostgreSQL 17, TypeORM 1.1
- **Frontend:** React 19, Vite 8, Effector 23, `@effector/router` 1.2, Mantine UI 9
- **Общий код:** `@kim/shared` — домен и правила валидации из текста ТЗ
- **Язык:** TypeScript 6.0 (не 7.x — NestJS опирается на legacy-декораторы)
- **Инструменты:** pnpm workspaces, ESLint (+ `eslint-plugin-effector`) и Prettier, lefthook + commitlint, тесты на встроенном раннере Node

Открытые риски, которые отслеживаем:

- КИМ упоминает серверное окружение с MySQL/PHP/Python; Node и PostgreSQL прямо не
  названы — надо уточнить у образовательной организации состав «набора фреймворков» и
  СУБД на общем сервере, а до ответа держать план отхода (ADR-0001).
- Офлайн-установка зависимостей обязательна и проверяется в Части 7 с отключённой сетью.
- Выбор ORM (ADR-0003) и схемы аутентификации (ADR-0004) ещё не сделан. Библиотека
  валидации выбрана — `class-validator`, оформление решения в ADR-0005 (Часть 2).

### Часть 2Б. План отхода: второй бэкенд на Python/MySQL — ✅ готово

Страховка на случай, если на площадке не окажется Node.js. КИМ прямо называет Python и
MySQL в перечне ПО, так что это самый вероятный доступный стек.

Ключевая мысль: **фронтенд переписывать не придётся.** Он обращается к относительному
`/api`, поэтому второй бэкенд, реализующий тот же контракт, подключается заменой прокси.
Отсюда и требование описать контракт в Части 2.

## 6. Запуск с нуля

Нужен **Node 20+** (разработка идёт на 24) и Docker для PostgreSQL.

```bash
# 1. pnpm. Версия запинена в package.json ("packageManager"),
#    поэтому pnpm сам переключится на нужную. Если pnpm нет вообще:
corepack enable                    # нужен corepack 0.36+, см. ADR-0002

# 2. Зависимости и git-хуки
pnpm install

# 3. Переменные окружения
cp .env.example .env

# 4. База данных (как поднять без Docker — docs/db-setup.md)
pnpm db:up

# 5. Всё приложение разом: shared в watch + api + web
pnpm dev
```

- API — http://localhost:3000/api (проверка: `GET /api/health`)
- Фронтенд — http://localhost:5173 (обращается к API по относительному `/api` через
  прокси Vite)

Полезное:

```bash
pnpm typecheck      # проверка типов во всех пакетах
pnpm lint           # ESLint по репозиторию
pnpm format         # Prettier с автофиксом
pnpm build          # production-сборка всех пакетов
pnpm db:reset       # пересоздать БД с нуля
pnpm mantine:docs   # обновить вендорённую документацию Mantine

pnpm --filter @kim/backend db:migrate     # применить миграции
pnpm --filter @kim/backend db:seed        # наполнить справочник помещений
pnpm --filter @kim/backend db:schema:log  # проверить, что база совпадает с кодом
pnpm --filter @kim/backend api:spec       # выгрузить контракт API в docs/api
pnpm test                                 # тесты всех пакетов

pnpm mantine:docs                         # офлайн-документация Mantine
pnpm router:docs                          # офлайн-документация @effector/router

pnpm e2e                                  # сквозные проверки в браузере
pnpm images                               # пересобрать изображения из assets/source

pnpm py:install                           # окружение запасного бэкенда на Python
pnpm py:seed                              # его схема и демонстрационные данные
pnpm py:dev                               # запуск → http://localhost:3001/api
pnpm shared:python                         # перенести правила из @kim/shared в Python
```

`pnpm e2e` требует поднятого стека (`pnpm dev`): он открывает настоящий Chrome и проходит
формы, переходы и защиту маршрутов. Размер окна задаётся переменными `E2E_WIDTH` и
`E2E_HEIGHT` — понадобится для мобильного макета 390×844 в Части 5.

Docker нужен только для удобства. Как поднять PostgreSQL без него и как перейти на
MySQL — [docs/db-setup.md](./docs/db-setup.md).

**Вызывать `pnpm` напрямую, а не `corepack pnpm ...`** — иначе вложенные вызовы в
скриптах падают с `ERR_PNPM_BAD_PM_VERSION`. Причина разобрана в
[ADR-0002](./docs/adr/0002-monorepo-and-package-manager.md).

Если git-хук мешает уложиться в экзаменационный таймер:

```bash
LEFTHOOK=0 git commit -m "..."
```
