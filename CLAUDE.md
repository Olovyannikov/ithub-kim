# CLAUDE.md

Подсказки для работы с этим репозиторием.

## Что это за проект

Тренировочное веб-приложение для подготовки к демонстрационному экзамену по
**КИМ 09.02.07-3-2027, Том 1 (инвариантная часть)**, специальность 09.02.07, квалификация
«Разработчик веб и мультимедийных приложений».

Предметная область задана КИМ: портал **«Конференции.РФ»** — бронирование помещений
(аудитория, коворкинг, кинозал) для проведения Всероссийских конференций.

**Это не обычный продуктовый проект.** Все решения оцениваются по двум осям: работает ли
это и укладывается ли в экзаменационные ограничения. Полный текст требований, таблица
баллов и план работ — в [README.md](./README.md).

## Главные ограничения, о которых нужно помнить всегда

1. **Таймер.** Задание 1 — 1 ч 30 мин на БД + ER-диаграмму + бэкенд + 5 страниц. Весь
   ДЭ БУ — 3 ч 30 мин. Решение, которое нельзя воспроизвести руками за отведённое время,
   бесполезно, каким бы правильным оно ни было.
2. **Нет интернета** на рабочих местах участников. Любая новая зависимость — это ещё один
   пакет, который надо заранее положить в офлайн-хранилище pnpm.
3. **Текст ТЗ — дословно.** Названия статусов, способов оплаты, типы помещений, текст
   ссылки «Еще не зарегистрированы? Регистрация», логин `Conf2027` — эксперт сверяет
   интерфейс с текстом КИМ. Эти строки живут в `packages/shared` и не переформулируются.
4. **Вес критериев.** Подсистема безопасности — 16 б., интерфейс пользователя — 15 б.
   При выборе между «красиво» и «надёжная авторизация/валидация/роли» выигрывает второе.

## Порядок работы

Работаем **строго по частям плана из README**, по порядку. Перед началом части —
ADR в `docs/adr/` с вариантами, решением и последствиями; номера зарезервированы в
[docs/adr/README.md](./docs/adr/README.md).

Правила для ADR:

- Раздел «Контекст» обязательно учитывает ограничения ДЭ (время, офлайн, площадка).
- Раздел «Связанные критерии КИМ» указывает затронутые критерии и баллы.
- Если решение проверено на практике и что-то пошло не так — это дописывается в ADR, а не
  теряется в переписке (пример: «Проверено на практике» в ADR-0002).

Не забегать вперёд: если решение относится к следующей части, оставить `TODO` со ссылкой
на номер ADR, а не «на всякий случай» зафиксировать выбор. Так уже сделано с
`ValidationPipe` в `apps/backend/src/main.ts` (ждёт ADR-0005).

## Стек и структура

```
apps/backend   @kim/backend   NestJS 12 + PostgreSQL
apps/frontend  @kim/frontend  React 19 + Vite 8 + Effector 23 + Mantine 9
packages/shared @kim/shared  домен, константы и правила валидации из текста ТЗ
docs/adr/                    архитектурные решения
docs/er/                     ER-диаграмма (требование задания)
docs/design/                 требования к дизайну и дизайн-концепция
```

TypeScript 6.0.x. **Не обновлять до 7.x**: NestJS опирается на `experimentalDecorators`
и `emitDecoratorMetadata`, совместимость нового компилятора не проверена (ADR-0001).

`packages/shared` собирается в CommonJS, потому что его потребляют две разные среды:
NestJS (CJS) и Vite (ESM с интеропом). Поэтому в `apps/frontend/vite.config.ts` стоит
`optimizeDeps.include: ['@kim/shared']` — без этого dev-режим ломается.

## Рабочие скиллы

Установлены два набора скиллов (глобально, в профиле пользователя — в репозитории их нет):

- **superpowers** (`obra/superpowers`, плагин v7.0.0) — процессные скиллы: `brainstorming`,
  `writing-plans`, `executing-plans`, `test-driven-development`, `systematic-debugging`,
  `verification-before-completion`, `requesting-code-review`, `using-git-worktrees` и другие.
- **effector-ecosystem** и **effector-fsd** (`demark-pro/skills`) — Effector, Farfetched,
  Atomic Router и размещение кода по слоям Feature-Sliced Design.

Как их применять в этом проекте:

| Когда                             | Скилл                                          |
| --------------------------------- | ---------------------------------------------- |
| Начало новой части плана          | `brainstorming`, затем `writing-plans`         |
| Код бэкенда с валидацией и ролями | `test-driven-development`                      |
| Модели и эффекты фронтенда        | `effector-ecosystem`                           |
| Структура слоёв фронтенда         | `effector-fsd` (решение — в ADR-0006)          |
| Любой баг или падающий тест       | `systematic-debugging` — до предложения правок |
| Перед закрытием части плана       | `verification-before-completion`               |

**Важная оговорка про экзамен.** Эти скиллы рассчитаны на вдумчивую разработку: планы,
TDD, отдельные worktree, ревью. В подготовке это ровно то, что нужно. В самом прогоне на
1 ч 30 мин полный цикл не укладывается — там работает заранее отрепетированная
последовательность, а не процесс. Поэтому: **процессные скиллы — для подготовки, скорость
и мышечная память — для экзамена.** Если скилл предлагает шаг, который на таймере
невыполним, это сигнал, что к экзамену надо отрепетировать эту часть до автоматизма, а не
что шаг надо выполнить в день экзамена.

## Фронтенд: слои и Effector

Структура — урезанный Feature-Sliced Design (ADR-0006). Правило импортов: **только вниз**,
`app → pages → entities → shared`, обратно — никогда. Каждый слайс отдаёт наружу только то,
что объявил в `index.ts`.

```
apps/frontend/src/
  app/        провайдеры, тема, запуск, роутер, общий layout
  pages/      по странице из ТЗ: model.ts (логика) + ui.tsx (разметка)
  entities/   session и далее application, room
  shared/     api, forms, routes, theme
```

Правила, от которых не отступаем:

1. **Компонент не содержит логики.** Только `useUnit` и разметка. Любое «если» про
   бизнес-правило — в `model.ts`.
2. **Связи через `sample`**, а не вызовы эффектов из обработчиков. Исключение — отправка
   формы, где событие приходит из DOM.
3. **Загрузка данных привязана к `route.opened`**, а не к монтированию компонента.
4. **События роутера тоже через `useUnit`**: `useUnit(routes.X.open)`, а не
   `routes.X.open()` в разметке — иначе теряется привязка к scope. Это ловит
   `eslint-plugin-effector`.
5. **Состояние запроса не хранить вручную**: `$pending` — из `effect.pending`, ошибка — из
   `effect.failData`.
6. **Никакого localStorage для сессии.** Признак «вошёл» — ответ `GET /api/auth/me`.
   Токен в httpOnly-cookie, читать его из JS нельзя по замыслу.
7. **Не зеркалить состояние Effector в состояние React** через `useEffect` + `setState`.
   Если нужно производное значение — считать его в модели (как `$serverErrors`).
8. **Приложение работает в Scope** (`fork` + `Provider`, см. `app/scope.ts`). Поэтому
   императивный запуск юнита — только `allSettled(unit, { scope, params })`, а в
   компонентах — только `useUnit`. Прямой вызов обновит глобальное состояние, а не то,
   которое видит интерфейс. За этим следит конфигурация `scope` в `eslint-plugin-effector`.
9. В тестах — `createWatch({ unit, scope, fn })`, а не `.watch`: подписка должна быть
   привязана к scope.

Роутер — **`@effector/router`**, не `atomic-router`: второе — прежнее имя библиотеки,
в npm по запросу «effector router» находится именно оно, и API там другой. Офлайн-копия
документации: `docs/stack/effector-router/`, обновляется `pnpm router:docs`.

В api-клиенте обязателен `credentials: 'include'` и относительный `/api`. Без первого
cookie не уедет, и это выглядит как «авторизация не работает»; без второго сборка
перестаёт быть переносимой на площадку.

## UI: Mantine

UI строится **только на Mantine**. Документация вендорена в репозиторий, потому что на
площадке ДЭ нет интернета, а КИМ предусматривает офлайн-справочник по технологиям:

- `docs/stack/mantine/getting-started.md` — установка, PostCSS, провайдер, темизация
- `docs/stack/mantine/llms-index.md` — индекс всех 445 страниц документации в
  LLM-формате: ищи нужный компонент здесь, потом тяни страницу
  `curl -sL https://mantine.dev/llms/<slug>.md`
- `pnpm mantine:docs` — обновить вендорённые файлы
- `pnpm mantine:docs:full` — скачать полный справочник (~4.6 МБ, вне git) перед экзаменом

Правила:

1. **Сначала искать готовый компонент в Mantine**, потом писать свой. Своя обёртка — только
   когда в библиотеке нет подходящего примитива, и с объяснением в коде почему.
2. **Не подмешивать другие UI-библиотеки и стилевые системы.** Mantine прямо документирует
   несовместимость с Tailwind, emotion и styled-components — см. вопрос
   «Can I use Mantine with Emotion/styled-components/tailwindcss?» в индексе.
3. **Стили — CSS-модули плюс `postcss-preset-mantine`.** Вложенные селекторы работают
   только в CSS-файлах, в inline-стилях их нет. Динамику делать через data-атрибуты,
   CSS-переменные или `Styles API`, а не через ветвление в JSX.
4. **Формы — `@mantine/form`.** Ошибки валидации выводятся на самой форме: это дословное
   требование Задания 2, п. 1–2. Правила берутся из `packages/shared/src/validation.ts`,
   а не пишутся заново в компоненте.
5. **Тема — через `createTheme` в `apps/frontend/src/theme.ts`.** Цвета, шрифты и размеры
   берутся из руководства по стилю заказчика (`docs/design/`), а не подбираются на глаз:
   это критерий «соответствие корпоративному стилю заказчика», 11 баллов.
6. **Точки разрыва — значения Mantine по умолчанию.** Менять их можно только в рамках
   ADR-0008, с обоснованием от макета 390×844.
7. Версии `@mantine/*` держать едиными: `@mantine/core` требует ровно совпадающую версию
   `@mantine/hooks`.

## Команды

Менеджер пакетов — **pnpm, версия запинена через `packageManager`**. Вызывать `pnpm`
**напрямую**, не через `corepack pnpm` (детали и причина — в ADR-0002).

```bash
pnpm install          # зависимости + git-хуки (lefthook)
pnpm dev              # shared в watch + api + web параллельно
pnpm dev:back         # только NestJS   → http://localhost:3000/api
pnpm dev:front        # только Vite     → http://localhost:5173
pnpm build            # сборка всех пакетов
pnpm typecheck        # проверка типов во всех пакетах
pnpm lint             # ESLint по репозиторию
pnpm format           # Prettier с автофиксом
pnpm db:up            # PostgreSQL в docker compose
pnpm db:reset          # пересоздать БД с нуля
pnpm mantine:docs     # обновить вендорённую документацию Mantine

pnpm --filter @kim/backend db:migrate            # применить миграции
pnpm --filter @kim/backend db:migrate:generate src/database/migrations/Name
pnpm --filter @kim/backend db:seed               # справочник помещений
pnpm --filter @kim/backend db:schema:log         # база совпадает с кодом?
pnpm --filter @kim/backend api:spec              # выгрузить контракт API
pnpm test                                        # тесты (node --test по dist-test)
pnpm router:docs                                 # офлайн-документация роутера
pnpm e2e                                         # сквозные проверки в браузере
```

`pnpm e2e` — свой драйвер Chrome через DevTools Protocol (`scripts/browser.mjs`), без
Playwright: тот тянет сборки браузеров на сотни мегабайт, а их пришлось бы класть в
офлайн-хранилище. Требует поднятого стека. Именно эти проверки находят то, что не видят
ни модульные тесты, ни запросы к API: формы, переходы и защиту маршрутов. Размер окна —
`E2E_WIDTH` и `E2E_HEIGHT`.

**Docker не обязателен** — его нет в перечне ПО из КИМ. Как поднять PostgreSQL локально
без контейнера и как перейти на MySQL: [docs/db-setup.md](./docs/db-setup.md).

CLI TypeORM работает по **собранному** `dist`, без `ts-node`: он несовместим с
TypeScript 6 и это минус одна зависимость в офлайн-хранилище. Поэтому скрипты миграций
сначала вызывают `build` — так и задумано, не «лишний шаг».

Фронтенд обращается к API по относительному `/api` через прокси Vite — одна и та же
сборка работает и локально, и за общим сервером на площадке ДЭ. Не прописывать
абсолютные URL бэкенда.

## Git

Conventional Commits, проверяются commitlint в хуке `commit-msg`. `pre-commit` гоняет
ESLint и Prettier по staged-файлам, `pre-push` — `typecheck`.

Аварийный обход, если хук мешает уложиться в таймер:

```bash
LEFTHOOK=0 git commit -m "..."
```

КИМ требует коммиты минимум в начале и в конце каждого задания — это часть оценки, а не
формальность.

## Чего не делать

- Не добавлять зависимости без необходимости: каждая попадает в офлайн-хранилище, которое
  придётся тащить на площадку.
- Не переименовывать строки из ТЗ (`packages/shared/src/domain.ts`) и не «улучшать»
  формулировки.
- Не разносить правила валидации по фронтенду и бэкенду: единственный источник —
  `packages/shared/src/validation.ts`.
- Не менять схему базы напрямую и не включать `synchronize`: только миграции. Включённый
  `synchronize: true` — документированный аварийный путь для экзамена (ADR-0003), а не
  режим разработки.
- Не писать регулярные выражения и тексты ошибок в DTO и компонентах: только импорт из
  `@kim/shared`. Это проверяемое глазами условие на ревью (ADR-0005).
- Не задавать цвета HEX-кодами и размеры шрифта по месту: только токены темы Mantine.
  Палитра и типографика заданы руководством по стилю заказчика — это 11 баллов.
- Не добавлять `UNIQUE` и прочие ограничения, которых нет в ТЗ: на проверке они дают
  отказ там, где заказчик его не просил. Email, например, намеренно не уникален.
- Не принимать архитектурные решения без ADR и не делать части плана вне очереди.
